# Jam Page As A Remote — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the page Sonora serves to a jam listener from a speaker into a remote control — transport, the live queue, playlists, favourites and lyrics — behind a per-device capability model.

**Architecture:** Additive throughout. New variants on the existing `FromReceiver` / `FromHost` enums in `crates/state/src/jam/wire.rs`; one new `watch` channel on `Serving` carrying a whole `Snapshot`, diffed per session so only changed messages reach the socket; commands travel the existing `ServerEvent` + `oneshot` bridge into `state::Jam`, which calls `Playback` and `Queue` the way `state::remote` already does for media keys. The audio path — the tap, the chunker, the clock, the lead negotiation, the scheduling loop in `page.html` — is not touched.

**Tech Stack:** Rust 2024, GPUI, tokio, hyper + tokio-tungstenite, serde_json over WebSocket text frames, Fluent for every string, one dependency-free HTML page.

**Spec:** `docs/superpowers/specs/2026-09-22-jam-page-design.md`

## Global Constraints

Copied from `CLAUDE.md` and the coordinator's standing instructions. Every task's requirements implicitly include this section.

- **Do not restructure** `wire.rs`, the `session()` select loop in `server.rs`, or the audio path in `page.html`. Add to them.
- **After every task**, all three must be clean:

```rust
#[derive(Clone, Copy, Debug, PartialEq, Eq)]
pub enum Cap {
    Add,
    Control,
    Browse,
    Favorite,
}

impl Cap {
    pub const ALL: [Cap; 4] = [Cap::Add, Cap::Control, Cap::Browse, Cap::Favorite];

    pub fn key(self) -> &'static str {
        match self {
            Cap::Add => "jam-cap-add",
            Cap::Control => "jam-cap-control",
            Cap::Browse => "jam-cap-browse",
            Cap::Favorite => "jam-cap-favorite",
        }
    }

    pub fn of(self, caps: &Caps) -> bool {
        match self {
            Cap::Add => caps.add,
            Cap::Control => caps.control,
            Cap::Browse => caps.browse,
            Cap::Favorite => caps.favorite,
        }
    }

    pub fn set(self, caps: &mut Caps, on: bool) {
        match self {
            Cap::Add => caps.add = on,
            Cap::Control => caps.control = on,
            Cap::Browse => caps.browse = on,
            Cap::Favorite => caps.favorite = on,
        }
    }
}
```

- [ ] **Step 1: Write the module**

Create `crates/state/src/jam/snapshot.rs`:

```rust
use std::collections::HashMap;

use super::wire::{Caps, FromHost, Who};

#[derive(Clone, Debug, Default, PartialEq, Eq)]
pub struct Seat {
    pub name: String,
    pub native: bool,
    pub device: String,
}

#[derive(Clone, Debug, Default, PartialEq, Eq)]
pub struct Snapshot {
    pub room: Vec<Seat>,
    pub grants: HashMap<String, Caps>,
}

impl Snapshot {
    pub fn can(&self, device: &str) -> Caps {
        self.grants.get(device).copied().unwrap_or_default()
    }
}

pub fn between(was: Option<&Snapshot>, now: &Snapshot, device: &str) -> Vec<FromHost> {
    let mut told = Vec::new();

    let can = now.can(device);
    if was.map(|was| was.can(device)) != Some(can) {
        told.push(FromHost::Grant { can });
    }

    if was.map(|was| &was.room) != Some(&now.room) {
        told.push(FromHost::Room {
            listeners: now.room.iter().map(seen).collect(),
            you: seat(now, device),
        });
    }

    told
}

fn seen(seat: &Seat) -> Who {
    Who {
        name: seat.name.clone(),
        native: seat.native,
    }
}

fn seat(now: &Snapshot, device: &str) -> i32 {
    now.room
        .iter()
        .position(|seat| seat.device == device)
        .map(|at| at as i32)
        .unwrap_or(-1)
}
```

`Seat` carries the device token and `Who` does not: a listener must never be handed another listener's token, so `you` is an index into the list rather than a token to compare.

- [ ] **Step 4: Add the token and ban helpers**

At the bottom of `server.rs`, beside `blocked` and `strike`:

```rust
fn tokened(device: String, at: &str) -> String {
    let device: String = device
        .chars()
        .filter(|glyph| glyph.is_ascii_alphanumeric())
        .take(TOKEN)
        .collect();
    match device.is_empty() {
        true => at.to_owned(),
        false => device,
    }
}

fn banned(shared: &Arc<Shared>, device: &str) -> bool {
    let kicked = match shared.kicked.lock() {
        Ok(kicked) => kicked,
        Err(poisoned) => poisoned.into_inner(),
    };
    kicked.contains(device)
}

fn ban(shared: &Arc<Shared>, device: &str) {
    let mut kicked = match shared.kicked.lock() {
        Ok(kicked) => kicked,
        Err(poisoned) => poisoned.into_inner(),
    };
    kicked.insert(device.to_owned());
}
```

A missing or unusable token falls back to the address, which is what happens today, so a receiver that never learned to send one still connects.

```rust
struct Bucket {
    left: f32,
    at: Instant,
}

impl Bucket {
    fn new() -> Self {
        Self {
            left: BURST,
            at: Instant::now(),
        }
    }

    fn spend(&mut self) -> bool {
        let now = Instant::now();
        self.left = (self.left + now.duration_since(self.at).as_secs_f32() * ACTS).min(BURST);

        true
    }
}
```

**Known deviation from the skill's default shape.** This plan has no test-first steps and no commit steps. `CLAUDE.md` forbids adding tests without being asked, and the user's standing rule forbids running `git commit` or `git push` at all. Verification is the three cargo checks plus the named manual checks against real devices, which is the only thing that proves a multi-room feature anyway.
