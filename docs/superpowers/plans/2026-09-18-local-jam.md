# A Jam On The Local Network — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Sonora taps its own decoded audio and sends it over the LAN as PCM, so a phone in a browser or a second Sonora becomes another speaker in the house.

**Architecture:** One tap in `music::audio::SmoothGain`, the layer all four providers share, moved behind the resampling so the stream has one format for the life of an `Output`. Each `Output` owns an `rtrb` ring; a dedicated chunker thread drains whichever one is live, converts to `i16`, and fans out over `tokio::sync::broadcast` to one WebSocket per receiver. The tap sits downstream of the `rodio::Player` queue, so seek, track change and gapless need no protocol at all.

**Tech Stack:** Rust, edition 2024, GPUI, tokio via `state::Io`, `rtrb`, `rodio`/`cpal`, `hyper` + `tokio-tungstenite`, `serde` + `serde_json`, `anyhow`.

**Spec:** `docs/superpowers/specs/2026-09-18-local-jam-design.md`

**Scope:** The whole of the spec's v1 — both receiver kinds, raw PCM, manual address.

- **Never run `git push`.** Ask the user before **every** commit; the commit commands in this plan are proposals, not authorisations.

`open` sizes the ring at **one second** — `format.samples(1000)` — not the spectrum's 8192. The consumer here is a scheduled thread, not a tight FFT loop.

`Cast::push` keeps the realtime contract exactly: never block, never allocate.

```rust
pub fn push(&mut self, sample: f32) {
    if self.producer.push(sample).is_err() {
        self.dropped.fetch_add(1, Ordering::Relaxed);
    }
}
```

`to_i16` clamps to `[-1.0, 1.0]` before scaling and maps a NaN to zero — a NaN reaching a speaker as `i16::MIN` is full-scale noise. Write into a reused `Vec<u8>` so the chunker allocates once.

- [ ] **Step 1: Pull the resampling forward**

- [ ] **Step 2: Add the second consumer**

`SmoothGain` gains `cast: Option<Cast>` beside `tap`, and a `with_cast` builder matching `with_tap` (`audio/mod.rs:150-153`). **Not a `Vec<Tap>`** — the two carry different signals:

```rust
}
if let Some(cast) = self.cast.as_mut() {
    cast.push(sample);
}
```

`tap` keeps `output` because the visualiser should show what this machine hears. `cast` takes `sample` because the host's volume knob is not the receiver's.

- [ ] **Step 3: Leave `resync` alone**

After step 1 the rate cannot change, so `resync` (`155-166`) never fires. Leave it: it costs one compare per frame and it is the thing that would catch a mistake in step 1.

- [ ] **Step 4: Pass `None` everywhere, for now**

`Output::open` takes `cast: Option<Cast>`; every call site passes `None` until task 3. The build stays green and this task is separately revertible.

```rust
pub const PROTOCOL: u32 = 1;
```

`Codec` is `#[serde(rename_all = "lowercase")]` with one variant, `Pcm16`. ### Task 6: The chunker and the broadcaster

**Tests: no.** A thread draining a ring; no harness.

**Files:**
- Create: `crates/state/src/jam/cast.rs`
- Modify: `crates/state/src/jam/mod.rs`, `crates/state/src/playback.rs`

**Interfaces:**
- Produces:
  ```rust
  pub struct Broadcast;                              // the handle the entity holds
  impl Broadcast {
      pub fn new(feeds: UnboundedReceiver<Feed>) -> Self;
      pub fn follow(&self, slug: Option<&'static str>);
      pub fn subscribe(&self) -> broadcast::Receiver<Arc<Chunk>>;
      pub fn format(&self) -> Option<Format>;
      pub fn origin(&self) -> u64;
  }
  pub struct Chunk { pub header: Header, pub bytes: Vec<u8>, pub mark: Option<MarkKind> }
  ```
- Consumed by: tasks 7, 9, 12.

- [ ] **Step 1: Keep the feeds**

The receiver end of the `UnboundedSender` task 3 built. Each `Feed` lands in a `HashMap<&'static str, Feed>`; a new `Feed` under an existing slug replaces it, which is how `restart_output` and `rebind` are handled — they throw an `Output` away and open a new one.

- [ ] **Step 2: The chunker thread**

A dedicated OS thread, not a tokio task: the timing must not inherit the async scheduler's jitter.

Per iteration:

1. read the live slug (an `ArcSwap`-style `Mutex<Option<&'static str>>` is enough — it changes rarely)
2. pop `format.samples(CHUNK_MS)` from that feed's consumer
3. if fewer arrived than asked for, sleep a fraction of a chunk and retry; if the ring stays dry past `QUIET_AFTER`, emit `MarkKind::Quiet` once and keep the sample counter running
4. take and clear `dropped`; non-zero means `MarkKind::Cut` and a rate-limited `log::warn!("jam: dropped {n} samples")`
5. `cast::to_i16` into a reused buffer, build the `Header`, send `Arc<Chunk>`

`CHUNK_MS` is 20.

- [ ] **Step 3: Follow the live engine**

`Broadcast::follow(slug)` is called from `state::Playback` wherever `current_slug()` can change — the same places `silence_others` is already called from. A change resets the sample counter and emits `MarkKind::Cut`: two rings have independent counts and splicing them would drift.

- [ ] **Step 4: Fan out**

`tokio::sync::broadcast` with a bounded buffer of about a second of chunks. A receiver task that falls behind gets `RecvError::Lagged(n)` — that is precisely "this client is too slow", and the response is to send it a `Cut` and let it re-anchor, never to slow the chunker down.

- [ ] **Step 5: Verify**

```bash

```

Then temporarily subscribe from a debug build and log the chunk rate. Expected: 50 chunks a second while playing, a `Quiet` shortly after pause, a `Cut` on a provider switch, and **zero** drops over a five-minute track. A drop here means the ring or the thread's cadence is wrong; fix it before task 9.

### Task 9: The server

**Tests: no.** Sockets.

**Files:**
- Create: `crates/state/src/jam/server.rs`
- Modify: `crates/state/src/jam/mod.rs`

**Interfaces:**
- Produces: `serve(port, code, broadcast, settings, events) -> Result<(u16, Task<()>)>` — the bound port and the task that owns the listener.
- Consumed by: task 7's `Jam::start`.

- [ ] **Step 1: One port, two routes**

`TcpListener::bind(("0.0.0.0", port))`; on `AddrInUse` retry once on port `0` and report what was bound, so two Sonoras on one machine are not a special case.

hyper serves both routes:

| Route | Response |
| --- | --- |
| `GET /c/<code>` | the page, `200`, `text/html; charset=utf-8` |
| `GET /c/<code>/ws` with the upgrade headers | `101`, handed to `tokio_tungstenite` |
| anything else | `404`, one line, no directory listing and no path echo |

Never build a filesystem path from the request. There is exactly one document and it is compiled in.

- [ ] **Step 2: Admission**

In order, and the order matters:

```
address is rate-limited   -> 429, close, do not compare the code
code is wrong             -> 404, close, count the failure
receivers at the cap      -> Refused { Full }
protocol mismatch in Hello-> Refused { Protocol }
otherwise                 -> Welcome { protocol, room, format, lead_ms, origin }
```

A wrong code returns `404` rather than `403` so a scanner cannot tell a wrong code from a wrong path.

- [ ] **Step 3: The rate limit**

A `HashMap<IpAddr, (usize, Instant)>`. Five refusals inside a minute blocks that address for a minute, **checked before the code is compared**. Six digits over TCP is otherwise enumerable in minutes; this is what makes the code defensible and it is not optional.

- [ ] **Step 4: One task per receiver**

Subscribe to the broadcast, write each `Chunk` as one binary message, and marks and `Now` as text. Read the receiver's `Ping` and answer `Pong` with `t1` and `t2` taken as late and as early as possible around the send.

On `RecvError::Lagged(n)`: log at debug, send `Mark { kind: Cut }`, and carry on. Never slow the chunker for a slow client.

On a write error or a close frame: drop the receiver and update the entity's list.

- [ ] **Step 5: Verify**

```bash

```

```bash

curl -i http://127.0.0.1:8990/c/000000              # 404
curl -i http://127.0.0.1:8990/../../etc/passwd      # 404, and no path in the body
```

- [ ] **Step 2: Scheduled buffers, not an AudioWorklet**

Read the spec's "Why scheduled buffers and not an AudioWorklet" first. In short: `AudioWorklet` needs a secure context and `http://192.168.x.x` is not one, so `audioWorklet.addModule()` is unavailable on the page a phone actually opens.

```js
const ctx = new AudioContext({ sampleRate: format.rate, latencyHint: "playback" });
// per chunk:
const buf = ctx.createBuffer(format.channels, frames, format.rate);
// de-interleave Int16Array into buf's channel data, /32768
const src = ctx.createBufferSource();
src.buffer = buf;
src.connect(gain);
src.start(playAt);            // ctx.currentTime domain
```

`playAt` walks forward by `frames / rate` from an anchor, so consecutive chunks abut sample-accurately. Re-anchor on a `Cut`, on the first chunk, and whenever `playAt` falls behind `ctx.currentTime`.

- [ ] **Step 3: The gesture**

An `AudioContext` starts `suspended`. The Play button's handler calls `ctx.resume()` — that is the gesture every browser requires, and there is no way around it.

- [ ] **Step 4: The offset slider**

±500 ms, added to `playAt`, remembered in `localStorage` per device. This is how a user trims out an output latency the page cannot measure: `AudioContext.outputLatency` is inconsistently implemented and covers neither the OS mixer nor a Bluetooth link, which alone adds 100–300 ms.

Wrap every `localStorage` access in `try`/`catch` — it throws in a private window.

- [ ] **Step 5: What it shows**

Room name, the current track from `Now`, Play/Stop, a buffer-health readout (how far ahead of `currentTime` the schedule runs) and the slider. The buffer readout is what lets a user tell a network problem from a sync problem.

- [ ] **Step 6: The strings come from Fluent**

The page carries `{{jam-page-play}}`-style placeholders and the server substitutes them with `i18n::lookup` as it serves the file — `state` already depends on `i18n`. **Never a bare English literal in the HTML.** The page follows the host's language; matching the receiver's would mean parsing `Accept-Language` and shipping every locale, which v1 does not do.

The keys themselves land in task 13; until then the substitution falls back to the key, which `i18n::lookup` already does.

### Task 11: The native receiver's audio

**Tests: no.** Audio path.

**Files:**
- Modify: `crates/music/src/cast.rs`, `crates/music/src/audio/mod.rs`

**Interfaces:**
- Produces:
  ```rust
  pub struct Sink;
  impl Sink {
      pub fn open(format: Format) -> Result<Self>;
      pub fn push(&self, first_sample: u64, samples: &[i16]);
      pub fn flush(&self);
      pub fn played(&self) -> u64;     // frames handed to the device
      pub fn nudge(&self, frames: i32);
  }
  ```
- Consumed by: task 12.

- [ ] **Step 1: Reuse `Output`, keep it private**

`Sink` owns an `Output` internally. `mod audio` **stays private**; what becomes public is the contract, not `Output`, `SmoothGain` or `Volume`. This mirrors `Player::spectrum()` (`music/src/lib.rs:202-204`), which hands out a view without handing out the engine.

- [ ] **Step 2: A jitter buffer as a rodio `Source`**

Implement `Source` over an `rtrb` consumer fed by `push`, appended once to the `Output`'s player. On underrun it yields silence rather than ending — a source that ends is gone for good, and a network hiccup must not end the session.

`push` converts `i16` back to `f32` off the audio thread.

- [ ] **Step 3: Correct by rate, never by seek**

`nudge(frames)` drops or duplicates that many frames at the next span boundary. Positive means the receiver is behind and must skip ahead. One frame at 44100 Hz is 22.7 µs — inaudible.

**Never `try_seek`.** A seek flushes, and a flush is a click. `flush` exists only for `Anchor`, where something already went wrong.

- [ ] **Step 4: Verify**

```bash
cargo check --workspace && cargo test --workspace && cargo clippy --workspace --all-targets
```

Then a throwaway binary or example that feeds `Sink` a generated sine from a file and calls `nudge(1)` once a second. Expected: continuous tone, no click on a nudge, and silence rather than a stall when the feed stops.

```
Nudge::Slew(n)   -> Sink::nudge(n), at most once per 50 ms
Nudge::Anchor    -> Sink::flush and re-anchor
```

## What this plan does not cover

Everything in the spec's [Out of scope for v1](../specs/2026-09-18-local-jam-design.md#out-of-scope-for-v1) — in particular Opus, mDNS, TLS, any control from a receiver, and a variable-ratio resampler.

The tap, the server, the page and the native receiver have no automated coverage: they run on a realtime callback thread, over sockets, and in a browser, and this repo has none of those harnesses. Task 15's matrix is the substitute.

Two things in this plan rest on readings that were not made. **Task 2 step 1** assumes `Mixer::add`'s second `UniformSourceIterator` passes an already-uniform stream through unchanged; that task checks it before relying on it. **Task 8** assumes turning on hyper's server feature adds no second major version to the tree; that task checks it with `cargo tree -d`. If either check fails, stop and report rather than working around it.
