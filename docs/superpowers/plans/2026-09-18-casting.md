# Casting To Chromecast — Implementation Plan

**Goal:** Sonora finds the Cast devices on the network and plays the jam's stream on one of
them, as a mode of its own beside the jam.

**Spec:** `docs/superpowers/specs/2026-09-18-casting-design.md`

**Scope:** Chromecast only. DLNA, Sonos and AirPlay are named in the spec and planned
separately, if at all.

## Global Constraints

- Branch is `feat/local-jam`. Ask before **every** commit; the commit lines here are
  proposals, not authorisations. Never `git push` without being asked.
- Conventional Commits, English, imperative, lowercase, no body, no assistant attribution.
  Scopes: `state`, `views`, `sonora`.
- `rust_cast` is synchronous: it belongs on its own thread, never on `io.spawn` beside async
  work. `mdns-sd` runs its own daemon thread and answers on a `flume` channel, which
  `state::Io` may await.
- Network work stays out of `music`; this is a `state` feature, like the jam.
- No colour, radius or size literals in the UI; no bare English string in the UI.
- After each task: `cargo fmt --all -- --check` clean, `cargo clippy --workspace --all-targets`
  with no new warning, `cargo test --workspace` green.

### Task 1: The endless WAV route — **done**

`GET /c/<code>/stream.wav` serves a RIFF header with `0xFFFFFFFF` sizes followed by the
broadcast's `i16` chunks, behind the same code and the same rate limit as the page. Landed in
`888641f`.

---

### Task 2: Prove a Chromecast accepts it

**Blocked, 2026-09-23.** There is no Cast device to hand, so steps 2 and 3 cannot be run.
Phases C to F stay unbuilt: a sender written against a device nobody can point it at is
guesswork, and step 3 exists precisely because the spec's latency numbers might not survive
contact with one. Anyone holding a Chromecast can settle this in five minutes with
`catt cast http://<host>:8990/c/<code>/stream.wav`.

**Tests: no.** This is a measurement, and it gates everything after it.

- [x] **Step 1: Play the URL by hand** — VLC picks up the stream and plays it, 2026-09-23.
  The chunked `audio/wav` with no `Content-Length` is accepted and decoded. The route holds;
  the device is still unproven.

- [ ] **Step 2: Hand the URL to the device**

Any existing sender will do — `catt cast <url>`, a phone's Cast button in VLC, or
`mkchromecast`. What matters is the answer to one question: **does the device play a chunked
`audio/wav` with no `Content-Length`?**

- [ ] **Step 3: Write down the delay**

Start a track, count the seconds until the Chromecast plays it. Under 3 s means the plan
holds. Over 10 s means `LIVE` and the bitrate are not enough and the spec's numbers were
optimistic — stop and report rather than building on it.

### Task 4: Discovery

**Tests: no.** Sockets.

**Files:** `crates/state/src/cast/mod.rs` (new), `crates/state/src/cast/find.rs` (new)

- [ ] Browse `_googlecast._tcp.local.` through `mdns-sd`, awaiting its `flume` channel from
      `state::Io`.
- [ ] Keep a `Vec<Device>`: friendly name (TXT key `fn`), model (`md`), address, port, id.
      A device that stops answering drops out after a grace period rather than instantly.
- [ ] The browse runs only while the panel that shows it is open, or while casting — it is a
      multicast conversation, not something to hold open all session.
- [ ] Verify beside Avahi: `avahi-browse -rt _googlecast._tcp` should still work while Sonora
      browses. If port 5353 cannot be shared on this machine, report it — that is a real
      finding, not a workaround to bury.

```

```

### Task 5: The cast session

**Files:** `crates/state/src/cast/session.rs` (new)

- [ ] `rust_cast` on its own thread, talking to the entity over a channel, the way the
      chunker already does.
- [ ] Connect with `connect_without_host_verification`, launch the Default Media Receiver
      (`CC1AD845`), then `LOAD` the stream URL with `stream_type: Live` and `duration: -1`.
- [ ] Keep the connection alive: answer `PING` with `PONG`, and treat a dropped socket as the
      end of the session rather than something to retry silently.
- [ ] `STOP` on leaving, and on the jam stopping.

```
git commit -m "feat(state): play the jam stream on a cast device"
```

### Task 6: The entity

**Files:** `crates/state/src/cast/mod.rs`, `crates/state/src/lib.rs`

- [ ] A `Cast` entity in the shape of `Jam`: `devices`, `casting: Option<Device>`, one stored
      `Task` per long-running loop, events for started, stopped and failed.
- [ ] Casting requires a jam to be hosting, because the URL is the jam's. Starting a cast
      with no jam running starts one first.
- [ ] Hang it in `Sonora` and construct it in `state::init`.

```
git commit -m "feat(state): add the cast entity"
```

---

### Task 7: What the host hears

**Files:** `crates/state/src/cast/mod.rs`

- [ ] Casting does **not** change the host's own playback, its position or its transport.
      The device is behind by seconds and that is stated in the UI, not compensated for.
- [ ] Stopping the jam stops the cast. Signing out of the provider that is playing leaves the
      cast running on silence, the same way a jam listener hears `Quiet`.

## What this plan does not cover

DLNA, Sonos and AirPlay. AirPlay in particular waits on one measurement — whether current
firmware still accepts a bare RAOP handshake — and on the judgement that ten to forty days is
worth it, which is the user's call and not this plan's.
